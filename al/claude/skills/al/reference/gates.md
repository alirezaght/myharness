# Sourced repository gates and CI context

## Service coverage

Before final proof and approval, AL must establish both affected-service coverage and required-check coverage. Scoped implementation may proceed while these facts are being discovered. The repository adapter supplies independently observed facts; the generic policy returns `identified`, `exhaustive`, or `incomplete`. `identified` runs checks for known affected services. `exhaustive` is allowed only when dependency uncertainty remains and both enumeration and check discovery are complete; it selects the whole potential-service universe. `incomplete` records specific verification gaps without blocking authorized scoped implementation. See [service-coverage.md](service-coverage.md) and its schema for the evidence fields and supported adapter boundaries.

Run a stage as one unfiltered invocation: `gates run --stage base` or `gates run --stage candidate`. The invocation materializes one disposable checkout and may reuse a successful local execution only when stage, manifest, pinned source identity, exact command and working directory, scope, declared source capabilities, declared environment, and timeout all match. Each manifest obligation still receives its own reservation, log, evidence entry, and gate association. Remote obligations always validate and execute independently.

Between gates, AL checks tracked content, the logical index, Git metadata, and ignored output. A successful check that creates only ignored scratch output keeps its evidence, discards the checkout and reuse cache, and causes the next executable gate to use a fresh checkout from the same pinned candidate. During this post-execution check, ignored generated symlinks are inspected without following them; if any appear, the successful gate keeps its evidence and the checkout is immediately discarded, with no reuse or subsequent launch in that checkout. Unsafe links present at initial capture, candidate materialization, or launch boundaries, and execution-relevant metadata changes, still fail closed. AL never cleans or modifies the source repository to recover a scratch checkout.

Candidate capture continues to include every candidate path, including vendored content. A gate scope may be narrow when its sourced dependencies justify that scope; it does not narrow complete candidate integrity or remove vendor paths from capture.

Gate discovery records obligations from source files and rules before implementation. CI jobs are identified by the pair `source.path` and `source.job`, and are bound to the source file hash. A job obligation carries its affected units, selected input paths, and the workflow/include dependency files needed to evaluate it. The manifest must preserve selected, anticipated, and previously declared paths and units. A replacement cannot erase a known job or narrow its required scope. Map each sourced job to its actual local or remote verification; do not infer a successful remote job from local evidence. Scanned implementation files are discovery inputs used to derive consumers and affected units; they are not policy rules. Body-only edits can invalidate evidence for affected consumers without changing the sourced rule set. Recompute those consumers and scopes at admission.

Remote lookup output is validated before provenance is read: the response and its `pipeline` and `commit` values must be objects; job and pipeline IDs must be positive integers (booleans do not count); job name, commit ID, and status must be nonempty strings; and an optional `web_url` must be a string or null. A non-null pipeline project ID must be a positive integer or nonempty string and match the manifest's project; omission or null remains supported for providers that do not return it. Malformed JSON, unsupported field types, or mismatched identity produce `INFRA`, preserve the lookup output in the log, and finalize the reservation rather than leaving evidence `RUNNING`. Only a matching job, project when supplied, pinned commit, and successful status can pass.

Local and remote gate processes are owned before spawn and run in process groups. On interruption or termination, AL stops and reaps owned descendants, drains their output, and finalizes the reservation as `INFRA` with its log and gate association before propagating cancellation. Finalization is serialized under the state lock; a cancelled operation cannot remain `RUNNING` or be recorded as a late `PASS`.

Local base and candidate gates run in a disposable checkout. Before overlaying candidate content, after the overlay, and before launch, the checkout is checked for unsafe symlinks. Relative links and chains are allowed only when they resolve to existing files or directories inside the checkout; `..` is allowed only while containment is maintained. Absolute, escaping, dangling, cyclic or excessive chains, unsupported targets, and `.git` paths are refused at these boundaries. After a successful gate, ignored generated symlinks are classified with non-following metadata inspection and force immediate checkout discard; nonignored drift and execution-relevant metadata changes remain failures. Gate working directories must also resolve to an existing contained directory outside `.git`. A rejected materialization is `INFRA` with no gate launch and no materialized fingerprint; it is not a gate failure or generated drift.

The bounded YAML reader handles the documented literal subset only. Dynamic includes, unsupported YAML constructs, unresolved anchors, and expressions outside the supported grammar remain `UNRESOLVED`; they are not treated as absent jobs or as satisfied obligations. Unknown job inventories and missing required verification block admission. A concrete, individually unresolved check remains unverified; `gates run` skips that check and `gates status` lists what was not verified. No pipeline PASS is implied. When a service's only sourced verification is such a job, the pipeline verifies the service (see Pipeline-verified CI jobs below). Local includes are followed with cycle, path, and count bounds. Job names and `source.job` are the concrete names from the merged sourced job graph. Include and workflow conditions are evaluated with three-valued results, so unknown conditions retain the obligation. Workflow `auto_cancel` is recognized only as scheduling metadata; cancellation settings do not remove job obligations.

Resolve includes, inheritance, and references while retaining every consulted source. Before considering an exclusion, preserve cumulative uncertainty from conditional definitions and unresolved workflow rules; malformed stage/environment structure, legacy `only`/`except`, and unsupported or malformed rule syntax also remain unresolved. A later unconditional definition cannot erase uncertainty from an earlier conditional contribution.

For a structurally valid job with trustworthy definition provenance, validate the complete supported `rules` list before applying its ordered first-match result. A conclusively false result, including a final `when: never`, omits the job from verification obligations. An unknown result remains `UNRESOLVED`; a true result, or a job without rules, proceeds to release/verification classification. This ordering lets known-false jobs with a valid custom stage or `environment.action: prepare` be excluded without guessing what their selected execution would do. If selected, those unsupported release identities remain `UNRESOLVED`; no prepare action becomes executable verification. Definite release stages and literal deployment environments with `action: start` or `action: stop` remain excluded, while verification jobs remain obligations. A release-like name without decisive stage or environment semantics stays `UNRESOLVED`.

Conditional-definition provenance is cumulative across includes, repeated definitions, inheritance, and `!reference` dependencies. If uncertainty could change whether a job exists or applies, retain the concrete job as `UNRESOLVED` over all selected task inputs and retain every contributing source/controller as a dependency. Proven-false includes contribute no definition; proven-true includes retain deterministic merge behavior. Source dependencies remain inventoried even when supported rules exclude a job, so changes to consulted rules invalidate prior manifests normally. Admission and currency use this same sourced inventory, so a replacement manifest cannot mark an uncertain obligation APPLICABLE or NOT_APPLICABLE, except by mapping it to its own verbatim `ci_recipe` (below).

Selected paths under `services/<service>/alembic/versions/` are migration changes, including deleted revisions and committed changes present in the candidate path inventory. They require the complete rollout assessment: expand/contract, deployment order, aggregator environment propagation, consumer deployment, and DLQ/redrive. Path matching is based on normalized components, so unrelated paths that merely contain a `versions` substring do not trigger this requirement.

A manifest may declare `ci_context` as `{ "profile": "merge_request_quality", "source": <typed artifact reference> }`. The referenced `ci-context` data artifact contains only `schema_version`, `profile`, the current `session_id`, `run_id`, `task_hash`, and `selection` provenance (`label` and optional `source_sha256`). It is content-addressed and bound to the active run and task. The task hash is derived from the immutable original plus verified amendment prefixes. An intact context tied to an earlier prefix may be recognized as historical while checking currency so the affected manifest can be replanned; it cannot supply the profile to a newly accepted manifest. Corrupt artifacts, unsupported/invented revision hashes, foreign runs, and mismatched bindings refuse. The artifact carries no variable map, secret, pipeline result, or execution evidence. The supervisor selects the profile and records provenance by capturing the JSON bytes with the existing `al_artifacts.snapshot_bytes(session_id, raw, "ci-context", source)` API, then includes that returned typed reference in the manifest. The Architect is read-only and does not choose or edit the context. See `schemas/ci-context-artifact.json` and `examples/ci-context-artifact.json`; the example is a template whose identity/hash placeholders must be replaced with current values.

`merge_request_quality` is a fixed planning profile, not a claim that CI ran: `CI_PIPELINE_SOURCE` is `merge_request_event`; `CI_MERGE_REQUEST_ID` is present for truthiness checks but its value is unknown; `CI_COMMIT_BRANCH`, `FASTLANE`, `BRANCH_ENV_CLEANUP`, and `SONAR_SCAN` are absent. Every other variable remains unknown. It does not import ambient process environment. Unknown variables, an unsupported profile name, malformed expressions, or unsupported syntax stay unresolved. The expression reader accepts a bounded boolean subset (variable truthiness, `==`/`!=` against quoted literals, `&&`, `||`, and parentheses) with three-valued evaluation. Presence without a concrete value cannot satisfy arbitrary equality. Regexes, variable expansion, and arbitrary shell evaluation are outside the contract. YAML input, include count/depth, expression size/token/depth, and path matching are bounded; input over those limits and unsupported syntax stay unresolved rather than being approximated. Glob/path matching is bounded and rooted in the repository; dynamic paths and unsafe or unsupported patterns remain unresolved.

The existing CLI flow is unchanged: `gates discover --paths-file <json> --base <pinned-base>` records the sourced inventory and `gates plan --file <manifest>` records an explicit plan. There is no new CLI or ambient environment switch; the supervisor prepares the artifact with the existing snapshot API and places its typed reference in the manifest before planning. The profile is applied consistently to workflow, local-include, and job rules while retaining ordered first-match behavior, changes, inheritance, and references. A source-proven excluded workflow does not become an empty satisfied inventory. Context and profile are part of manifest identity: changing either requires a replacement manifest and fresh base/candidate evidence under the existing recovery rules. Supplying the optional typed context changes only planning applicability. It does not create CI jobs, execute recipes, access GitLab, or replace `gates run`, remote evidence, base-gate decisions, or candidate-gate requirements. A remote job still requires actual project, job, pipeline, commit, and successful-status provenance; a planning profile never manufactures it. If context or applicability is unknown, resolve the source semantics or keep the obligation unresolved before advancing.

### Discovery on large repositories

`gates discover` builds one repository inventory per run. Requested directories are expanded to their members first, the expanded set is analysed once, and validating the resulting manifest reuses that same inventory instead of rebuilding it. Every phase prints a progress line (phase, items done/total, elapsed); silent phases print a `still working` heartbeat every 15 seconds that carries the items processed so far out of the phase total when the phase knows it (`still working · 8192/34210 items processed so far`), so a slow phase (the count keeps moving) is told apart from a stuck one. Binding scanned inputs to units is one ancestor lookup per scanned source, and the literal consumers of every opaque, symlink or gitlink boundary are found in one shared pass over repository sources (printed as `finding source consumers of repository boundaries`), not one full re-read per boundary. Repository analysis is recorded as facts in one content-addressed store per repository (`~/.local/state/al-distribution/analysis-index/<hash of the git common dir>/`), shared by every worktree and task of that repository. A fact is a pure function of content-addressed inputs and is keyed by the digest of the code that produces it (its module closure) and the hash of every input it read: per blob, a source's import observations and its literal-reference runs; per Git object, a blob's sha256; per question, a literal-reference answer. A later discovery, `gates plan`, a discovery in another worktree, or one after an AL release that did not change the analysers, reads only blobs it has not seen and replays the stored facts; uncommitted and untracked files are hashed like any blob. Reuse is exact: manifests are byte-identical to a cold run with the store disabled. The store holds immutable packs written atomically (temp file and rename), without locks, so concurrent commands in different worktrees never wait on each other; least-recently-used packs are deleted beyond its size and count bounds, and an evicted, corrupt, foreign or symlinked entry is a miss and is recomputed. Directories are 0700 and files 0600. `AL_ANALYSIS_CACHE=0` disables the store; `AL_ANALYSIS_INDEX_DIR` relocates it. The working copy is captured as one Git tree through a private index kept in the worktree's own Git directory (`git add -A` and `git write-tree` against `al-snapshot.index`, seeded from the real index with its timestamp so Git's racy-clean check still applies, assume-unchanged and skip-worktree flags cleared so those files are checked against the disk); the user's index and working tree are never touched. Git's stat cache and `core.fsmonitor` make it incremental, and the tree vouches for a file's content when the file is a regular file of the blob's size, unchanged for the racy window before the capture, and not subject to Git conversions (`text`, `eol`, `filter`, `ident`, `working-tree-encoding` attributes or `core.autocrlf`); every other file is read directly. AL's own membership rules, symlink, nested-repository and torn-capture checks are unchanged. `al_snapshot.input_tree(st, paths)` returns the tree hash of the working copy restricted to some paths: equal hashes mean byte-identical inputs. Snapshot trees a run must keep are pinned under `refs/al/snapshots/<run>/`. `gates plan` does not repeat discovery: validating a manifest records, in the run's runtime directory, the observations of the capture it depended on (membership listing, path, absence, pattern-match and source observations), keyed by the manifest, the run-state inputs, HEAD, the index and gitlink rows, the environment and PATH tools, and the code digest of the inventory. A later validation of the same question (normally `gates plan` on the manifest `gates discover` just produced) re-observes them with the capture's own racy-clean and drift rules instead of computing a fresh inventory; any difference, or an unreadable or forged record, computes a fresh inventory.

Discovery does not hold the run admission lock while it analyses. It reads the run state under a short lock, analyses, then takes the lock briefly to save. Writers, amendments and other commands keep working on the currently admitted plan meanwhile. When saving, discovery checks that the run state it depended on (base, prior manifests, task changes, CI context) is unchanged, or that its inventory inputs are still identical; otherwise it saves nothing and refuses with the exact `gates discover ...` command to re-run. If a discovery input changes while a writer is ACTIVE (a parallel writer still editing), discovery saves nothing and refuses with `writer <id> still active; run after writer finish`, naming the writer that owns the moving path and the command to re-run; with no writer active, a capture drift is reported as such. A command that waits for the run lock prints which command holds it.

`gates discover ... --output <file>` and `gates plan --file <manifest> --output <file>` write the manifest JSON atomically to the file (a temporary file in the same directory, then rename) and print only one line: `gate manifest <file> sha256=<hex> gates=<n> paths=<n>`. Without `--output` the manifest JSON is printed to stdout as before. `--output` is accepted by every `gates discover` form (plain, `--bounded`, `--extend`, in any option order). A run executes with the runtime pinned when it started, so a run started on AL 0.1.25 or earlier refuses `--output` with `unrecognized arguments` even after a newer AL is installed; start a new run on the current AL, or omit `--output` and redirect stdout. If `--base <ref>` no longer resolves to the run's pinned merge base (for example `origin/main` moved after the run started), discovery refuses, prints the pinned merge-base SHA and the exact command to re-run with `--base <sha>`; `--base pinned-base` always names the pinned base.

`gates discover --extend <manifest> --paths-file <json>` adds paths to an existing manifest: `current` (the latest manifest), a recorded manifest's stored path or sha256, or a manifest file. The new manifest plans the union of both path sets. Because a manifest carries one coverage declaration that later currency checks re-derive from the full planned path set, the union is analysed in one pass rather than merged from a partial analysis.

`gates discover --bounded` bounds reach analysis. Units that hold a declared or changed path still get the full per-file analysis. A unit reached only through a shared package or consumer edge is recorded as affected with inherited checks: its CI checks are selected from its affected consumer files (or, without one, from the unit directory, as for a declared directory), not from every file in the unit. The manifest records `"discovery_mode": "bounded"`, and its validation, refresh and currency checks re-ask the bounded question. Bounded discovery can select fewer CI jobs for reached units than the default (for example, a job whose `rules:changes` names only test files of a reached unit), so it is opt-in.

Every `writer start` rechecks manifest currency under the admission lock (sourced rule hashes and touched units), then validates its declared paths against the manifest's paths and units. An exact file entry covers only that file. A declared directory covers its descendants by path components, and `.` covers the repository; a file does not grant sibling, parent, or similarly prefixed directory coverage. A changed rule source, new rule source or new unit whose path the plan already covers refreshes the manifest automatically: AL rediscovers the planned paths, records the refresh in `gate_refreshes`, and carries base runs, decisions and exceptions of gates whose definition is unchanged. A path, unit or rule outside the planned paths is refused without changing state until a valid replacement plan is recorded. Base gates no longer hold back writers; they must pass, or carry a recorded decision, before review. The full repository inventory runs at discovery, at `gates plan` and once at review start. Ordinary edits within an already covered file or directory do not require replanning by themselves.

When source rules or the derived obligation inventory become stale during an unfinished exceptional phase (`PSEUDOCODE`, `PLAN_CONFLICT`, `IMPLEMENTATION`, `REWORK`, or `CORRECTION`), ordinary replanning is allowed only after `SPEC_READY` and while no writer or check is active or unresolved. AL records a checkpoint-bound recovery marker and accepts a replacement manifest without changing the retained phase or its completion history. A current manifest does not grant this path. Planning does not clear recovery: current obligations and applicable base gates must pass before phase advancement or a new writer. Present but corrupt recovery markers remain hard refusals.

Prospective coverage is evaluated for the replacement request before deciding whether an extension is needed. Replacement is justified by stale sourced rules or a demonstrated gap in prospective paths/obligations, not by an unchanged manifest. Planning preserves the retained phase and completion history. Writer admission enforces actual scope, identity, ownership and containment; missing currency, coverage and base readiness remain verification obligations, with conservative selection and repair.

## Gitlink evidence capabilities

Gate manifests may declare an optional `sources` array on each gate. Evidence planning and execution accept the same declarations through `--sources-file <json>`, where the file contains an array of `{ "path": "vendor/lib", "capability": "parent-entry" }` objects. Each path is normalized relative to the parent repository and identifies a gitlink boundary. Omission is equivalent to an empty array for ordinary scopes.

`parent-entry` declares that a check depends on the parent repository's gitlink entry. AL fingerprints the staged and effective parent pointers, so a pointer change invalidates evidence. It proves the selected pointer only; the child repository's files and uncommitted content remain opaque. Broad scopes such as `.` do not implicitly claim child-content coverage. Any scope intersecting a gitlink needs a capability, including when the scope is the gitlink path itself; discovery declares `parent-entry` by default for every gitlink a gate's scope covers, since a check outside the child repository sees only its pointer. Scope or working directory inside a child repository requires child-content verification.

`child-content` is reserved for an execution rooted in the child repository. This version reports that capability as unsupported and directs the operator to run AL from that child root; it does not import child-run evidence into a parent run. AL does not infer dependencies by inspecting command strings. Existing evidence with no `sources` remains usable for ordinary scopes, while legacy evidence whose scope overlaps a gitlink cannot establish which content it covered and is treated as unresolved until rerun with an explicit capability.

Parent snapshots and isolated candidates materialize the effective parent gitlink pointer without initializing, fetching, or copying child contents. The parent index pointer and an initialized child's current `HEAD` are recorded separately; the effective candidate uses the latter. Dirty, unavailable, or failed child inspection is reported as uncaptured child state. Checks disjoint from that boundary may still run, but approval cannot claim that opaque child changes were reviewed or tested. Because a complete-candidate snapshot cannot safely distinguish pre-existing child dirt from task changes, AL reports the limitation and blocks approval when such child work is present. Isolation reproduces parent entries and ordinary files only; it does not reconstruct child worktrees or their indexes.

## Review-hook state

A repository review hook that writes under `.git` (for example `.git/codex-review`) is supported only through an explicit gate declaration: `"review_state": {"path": ".git/codex-review"}` on an applicable local gate. The path is one isolated `.git/<name>` location (up to three literal segments); Git's own metadata (`objects`, `refs`, `hooks`, `index`, `config`, `HEAD`, `logs`, `worktrees`, ...) is never accepted, and `.git` writes in general remain refused. A gate without a declaration whose only change is one new, non-Git `.git/<name>` location (absent before the run) has that location removed after execution; the evidence note records it. Any other drift fails and the log lists the changed paths, with the `review_state` declaration to add when the change is a single hook state location.

In the disposable checkout the declared location must be absent before each execution, so stale or foreign review state cannot carry into a gate. After the command ends (and its process group is reaped) whatever the hook left there is captured, including its absence, directory modes and file bytes and modes, bounded to 4,096 entries / 16 MiB; symbolic links, hard-linked files, special files and files that change during capture are refused. The location is then removed, after which the ordinary metadata drift check still fails any other `.git` write. The capture is retained as an immutable `review-hook-state-v1` artifact bound to the run, evidence reservation, manifest, gate, stage, invocation, execution identity and candidate (or base) fingerprint, and the evidence records its digest metadata. Gate validation requires that artifact to be intact and bound to the current candidate; missing, stale, foreign or altered state invalidates the gate. Declared-state gates always execute fresh rather than reusing an execution receipt, and the declaration is part of the execution key and preserved across rediscovery. The source repository's own `.git` never receives review state.

## Baseline exceptions

`fix` commits the task to repairing a failed base gate and `stop`/`defer` stop the run. A distinct `gates decision --id <gate> --action exception --source <explicit authorization> --reason <why>` records that the current exact unchanged-base failure of one gate is accepted for implementation admission while its repair stays outside the task. It requires the latest current-manifest base evidence of that gate to be FAIL with an intact log, and writes an append-only, immutable `baseline-exception-v1` authorization artifact binding the session, run, pinned base, manifest, gate command (`argv`, `cwd`, `scope`, `sources`, execution kind), declared environment names and fingerprint, failed evidence, reservation, exit, log hash and execution identity.

Base readiness accepts that one failure only while every bound value still matches; a new manifest or base run, a changed command or declared environment value, an altered log or a forged artifact makes the exception stale and the gate blocks again. The evidence stays FAIL and `gates status` lists exceptions separately from gate results. An exception satisfies no other obligation: `gates run --stage base --resume` still executes every remaining base gate, and other failures still block. Candidate gates always run and report failures honestly; only new failures block.

### Pre-existing candidate failures

A candidate gate that fails identically on the unchanged base is pre-existing. It is reported (evidence stays FAIL, `gates status` lists it under `unverified` with its reason) and does not block; a base exception covers that identical candidate failure and the note says so. Only a new failure blocks. A base `fix` decision commits the task to the repair, so that gate must pass. A gate whose units the change does not touch and that also failed at base stays pre-existing as before. `gates run --stage candidate` continues past a pre-existing failure and exits 0 when it is the only kind of failure.

"Identical" means the same command (`argv`, `cwd`) and the same exit code, compared after normalising both logs: AL's header lines, disposable checkout paths, line/column positions (`file.py:12:5`, `(l.12)`, `line 12`), durations, colours, hashes and timestamps are removed and whitespace is collapsed (`al_gate_signature.py`). When the candidate log has finding lines (path:line diagnostics, test ids, import chains, error/fail/broken/forbidden/violation wording), they are compared as a multiset: every finding, counted with multiplicity, must also appear at base, so a new finding or one more occurrence of a known one blocks, while a moved line or a changed file count does not. Without recognisable findings the fallback is the same exit code and the same SHA-256 digest of all normalised output lines.

## Advisory CI steps

A CI step whose failure never fails the pipeline is informational. Discovery honours the sourced recipe (`al_ci_advisory.py`), generically and without looking for any repository's helper names:

- GitLab `allow_failure: true` or `allow_failure: {exit_codes: [...]}` on the job, or on every rule that can select it (a rule's own `allow_failure` overrides the job's); `after_script` lines, whose failures GitLab ignores.
- GitHub a literal `continue-on-error: true` on the job (the job is advisory) or on a step (the step is left out of the mapped check). An expression stays unsupported.
- Shell: `cmd || true`, `|| :`, `|| exit 0`, `|| return 0` or `|| echo ...`; and a shell function that runs its arguments (`"$@"`) with the failure swallowed (`"$@" || true`, `if ! "$@"; then echo ...; fi`, or after `set +e` with a benign last statement) and that records nothing for a later check (no assignment, counter, file write or non-zero `return`/`exit` after the call). A helper function that runs the tool is advisory when every call of it is. Scripts that CI runs or sources (`sh x.sh`, `./x.sh`, `source x`, `. x`) are followed, bounded to 64 files of 1 MiB, and bound as rule sources.

A GitLab job line that swallows its failure is left out of the mapped command and recorded as `advisory_steps`; a job whose every line swallows its failure, or that allows failure, becomes an advisory obligation. A check the repository configures outside CI (for example `[tool.importlinter]` in `pyproject.toml`) is advisory when the CI recipes invoke that tool at least once and every invocation is advisory; one blocking invocation keeps it required. The reason notes when the CI inventory was incomplete.

An advisory gate has `"required": false` and an `"advisory"` reason. It still runs at base and candidate, and its result is a note: it never needs a base decision, never blocks review or approval, and `gates status` lists it under `unverified` with `"advisory": true`. Only a reconstructed advisory step can mark a gate advisory: `gates plan` refuses an `advisory` flag that discovery does not reproduce, and a sourced check cannot be silently made non-required.

## Pipeline-verified CI jobs

A sourced CI job AL cannot run locally (its rules depend on pipeline variables such as `$CI_PIPELINE_SOURCE`, or it needs a runner image, job variables, services, deploy tools or shell syntax outside the literal subset) stays an `UNRESOLVED` gate: the pipeline verifies it. It is an unverified obligation, never a blocker. Its reason names what is unresolved and how to resolve it, and `gates status` and the review packet's `unverified` list show it.

When a service's verification check would otherwise be missing and one or more concretely enumerated, task-relevant, non-advisory, non-release jobs covering that service are left to the pipeline, discovery records the service under `service_coverage.semantic_requirements.checks.pipeline_verified` (unit, obligation, jobs) instead of a `missing-verification-check` coverage gap; `gates status` lists it under `unverified` with `"pipeline_verified": true`. Unknown CI inventories, advisory jobs and definite release/deploy jobs never qualify, and a service whose only jobs are mapped but do not cover it keeps the gap.

Two paths resolve such a job:

- **Verbatim recipe.** When every definition that may run agrees on literal `before_script` + `script` lines, none of which reaches outside the checkout (deploy, push, publish, container or cloud tools), discovery offers `ci_recipe: {"argv": ["sh", "-e", "-c", <lines>], "cwd": ".", "execution_kind": "local", "env_names": ["PATH"], "semantics": ...}` on the gate. A planner maps the job by setting the gate `"applicability": "APPLICABLE"` and `"argv"` to exactly `ci_recipe.argv`, keeping `ci_recipe` unchanged. `gates plan` accepts it only when the recipe matches the one it reconstructs from the source; any other argv for an unresolved job is refused. The gate then runs at base and candidate like any required local gate (a new candidate failure blocks; an identical base failure is pre-existing). The runner image, job variables and services are not reproduced, so `gates status` notes the mapping (`"verified_by": "local verbatim CI recipe"`).
- **Remote CI evidence.** `gates ci-evidence --id <gate> --status success|failed|canceled|skipped|manual|running|pending|created --url <pipeline-or-job-url> [--pipeline-id N] [--job-id N] [--commit SHA] [--note TEXT]` records the pipeline's own result for an unresolved (or recipe-mapped) CI gate, bound to the current manifest and candidate. AL does not contact the provider: the record is supervisor-recorded (`"verified_by_al": false`), shown to the reviewer in `gates status` and the review packet (`"verified_by": "remote CI evidence (supervisor-recorded)"`, with `commit_matches_head` and `current`), marked stale after the manifest or candidate changes, and never a passing gate or a blocker. A provider-attested remote gate (GitHub `remote`, GitLab `remote: {"provider": "gitlab", "project_id", "job_name"}` with `glab api projects/<id>/jobs/<job>`) remains the only remote PASS.

## Gate environment

Gate checkouts do not inherit ambient settings that switch off or redirect dependency installation: `UV_NO_SYNC`, `UV_OFFLINE`, `UV_FROZEN`, `UV_LOCKED`, `UV_NO_INSTALL_*`, `UV_NO_BUILD*`, `UV_NO_INDEX`, `VIRTUAL_ENV`, `PIP_NO_INDEX`, `PIP_NO_DEPS`, `PIP_REQUIRE_VIRTUALENV`, npm/yarn offline switches and `COREPACK_ENABLE_NETWORK`. They are removed before a gate or its dependency setup runs, and the log records `environment scrubbed: <names>`. A gate that declares one of these names in `env_names` keeps it, because declared names are part of its environment fingerprint.

## Action cache

`gates run --stage base|candidate` looks each local gate up in the repository's action cache (see
[evidence.md](evidence.md#action-cache-reuse-across-runs-tasks-and-worktrees)) before it materializes
a checkout. The key is the gate's argv, cwd, category, scope and sources, its declared environment plus
the scrubbed-environment policy above, the tool identity and lockfiles, and the input tree: the base
commit's tree at base, the worktree's at candidate, over the gate's scope plus its package. Base gates
on an unchanged target branch therefore run once for every task and worktree, and an unchanged
candidate reuses the base result. A hit is recorded as the gate's run (`reused from run <run> (<entry>)`
in the output, `reused_from` in the stage report, `reused_results` in the review packet). A cached FAIL
is reused; INFRA, TORN and timeouts never are. An explicit retry (`--retry-failed`, or `--resume --id <gate>`) always executes and replaces the record,
`--no-cache` skips the cache, a gate with `"hermetic": false` is never cached, and `AL_ACTION_CACHE=0`
disables it. Remote, package-script, review-state and pytest-guarded gates always execute.

## Repository pytest suites

A locally mapped CI job's `uv run pytest` step is executed through AL's guarded pytest runner exactly as the job declares it: the repository's configured `testpaths`, only reviewed non-masking options, and no deselection, skips or expected failures. A literal marker expression (`pytest -m "not browser"`) is the one supported selection: it must be identifiers combined with `not`, `and`, `or` and parentheses, it may come only from the job's own command (never from `addopts` or `PYTEST_ADDOPTS`), it is part of the execution profile and signature, and every deselected test is recorded in the evidence. Declared `markers` in the pytest configuration are accepted. Tests a marker excludes belong to whatever job runs them (for example a separate browser workflow); AL only verifies the jobs that apply to the planned CI context.

CI relevance is source-backed. Supported false applicability rules may defer a disjoint job before demanding execution support. Deferred sources stay currency dependencies. Unsupported global/includes and unknown shared impact remain unresolved for final verification; diagnostic wording cannot decide structural completeness. Known concrete extra jobs cannot replace a missing check or invalidate an independently complete required verification chain.

Pre-commit hooks prepare supported locked dependencies inside their owned disposable checkout before running. Setup uses uv sync --locked, npm ci, or pnpm install --frozen-lockfile according to source lockfiles. Missing tooling or failed setup is INFRA and the hook is NOT_RUN; an executed hook failure is FAIL. Ambient node_modules are never borrowed. Required setup/transport gaps remain unsatisfied and cannot be waived by log text. Provider pending/manual/canceled results retain their outcome and remain INFRA/BLOCKED, while an actual failed provider job remains FAIL.


## Source-bound package checks

The repository adapter inventories literal JavaScript package scripts and their
source-bound CI selections. It retains the selected package manager, lock,
workspace, lifecycle and configuration inputs. It does not create missing
manifests or checks, add flags, suppress hooks, or turn a watch command into a
terminating check. Python applications reuse supported literal Python project
context; missing source context remains a discovery gap.

Execution and semantic verification are separate. Finite contracts cover Node
syntax/tests, TypeScript `--noEmit`, ESLint, terminating Vitest and Jest forms.
Unknown versions, dynamic configuration, external plugins, executable aliases,
unqualified inherited TypeScript scope and unsupported install lifecycle remain
unverified. A visible, policy-allowed check is never proof merely because it exits
zero. Reported failures remain FAIL, no-test results remain EMPTY, and unavailable
execution remains INFRA. Only an otherwise verified result can be downgraded by
runtime uncertainty. The framework parser fixtures are not live framework
certifications; actual runtime qualification is bounded to the recorded versions.

Locked setup uses the selected package root. Package preflight runs before setup
or version children. New package output is bounded in memory; durable records
contain typed results, counts, sizes and hashes rather than raw child output or
exception text. Existing generic source archives and legacy precommit logs are
outside that output guarantee. Inspection failure stops owned children and
records cleanup through the standard evidence fields. Unknown cleanup stays
unresolved even when a baseline failure decision exists.

These adapters do not waive repository-wide v1 coverage, root/shared obligations,
unknown CI conditions or final proof. Scoped implementation can continue under
the existing readiness policy while those verification obligations are repaired.


GitHub quality evidence supports the current literal Ubuntu apt/ripgrep and macOS brew/ripgrep recipes as **remote required**. Neither package command executes locally. Both platform jobs remain separate mandatory source obligations. Default checkout and setup-uv, Python install, locked sync, ruff check, format check, repository-mandated nonbrowser pytest and build are bound in source order with workflow and dependency hashes. Other shell syntax, matrices, reusable workflows, custom names, conditions and failure masking remain unavailable.

Discovery emits `execution_kind: remote`, `argv: ["gh", "api"]` and an independently reconstructed `remote_source`. A planner adds only `remote: {"provider":"github", "repository_id":42, "run_id":123, "attempt":1, "job_id":456}` using actual positive numeric identifiers. These example numbers confer no evidence. Selection cannot alter source obligations, runner, ordered steps, source signature or either platform requirement. A missing selection is unavailable, never a successful local gate.

The helper generates fixed github.com read-only GETs for `/repos/{owner}/{repo}`, `/actions/runs/{id}`, `/actions/runs/{id}/attempts/{attempt}`, the attempt's complete bounded jobs listing, and `/actions/jobs/{id}`. Canonical repository owner/name comes from the literal HTTPS or SSH GitHub origin, with no ambient gh repository default. The independent repository endpoint binds numeric repository identity; selected IDs must agree. Run and attempt must be successful completed push events for the exact committed candidate (or independently pinned base), workflow ID/path and repository/head repository. The unique selected job must agree across the complete listing and direct lookup, including runner label and every sourced step's ordered number/name and successful status. Metadata is refetched to refuse changed attempts; source, origin, workflow membership and committed dependency bytes are rechecked. Dirty/untracked candidates refuse. Runner labels attest the requested platform, not an exact hosted image version.

Each read has private bounded output (2 MiB), the listing has at most ten pages of 100 jobs, and the whole lookup has a maximum 120-second deadline. Owned subprocesses must settle; unknown cleanup, missing steps, malformed/inaccessible responses, auth/rate failures, skipped/neutral/cancelled/pending jobs and timeouts remain INFRA. Durable provenance contains closed validated fields and response hashes, never raw API bodies, exceptions or stderr. No dispatch, rerun, approval, cancellation, credential provisioning or write endpoint is added. Existing read authentication and caller permissions still apply.

The unnamed-step mapping is deliberately exact (`Run <literal uses/run>`, plus known successful GitHub setup/post/completion wrappers). Mock fixtures validate this closed contract but do not qualify genuine GitHub naming or API behavior. Qualify the actual published candidate through genuine read-only API responses before relying on its CI job attestation. Browser, containment, native/business acceptance and deferred manual/tag workflows retain their separate required evidence.

A literal `collect_ignore` is recognized only when every canonical relative path is proved disjoint from all independently sourced explicit collection roots. The defining conftest/config bytes, ignored paths and disjoint-root proof remain bound in the verification signature. Default root `.`, overlaps, traversal, absolute paths, glob exclusions, dynamic mutation, plugins and collection hooks remain unavailable. This classification does not remove declared tests or attest per-source application coverage.


GitHub remote semantics v2 distinguishes `CI_JOB_ATTESTATION` from guarded pytest qualification. Successful provider responses record `ci_job_attestation.status: PASS` and `pytest_guard_status: UNAVAILABLE`; the mandatory gate result remains INFRA. Plain `uv run pytest` success does not attest the sourced execution guard's no-skip/no-xfail or runtime plugin checks. Inventory retains the guarded-pytest gap and cannot bind `verification-root` from these remote jobs. Historical provider-only PASS receipts are also unavailable for full verification. No supplemental guard-proof acceptance path exists in this adapter, and self-asserted guard flags confer no credit. Existing local guarded pytest and GitLab behavior retain their existing contracts. Genuine provider qualification establishes only this bounded job attestation; final verification still requires actual authenticated guard proof and separate mandatory acceptance evidence.
