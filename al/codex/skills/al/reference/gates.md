# Sourced repository gates and CI context

## Service coverage

Before admitting a phase, AL must establish both affected-service coverage and required-check coverage. The repository adapter supplies independently observed facts; the generic policy returns `identified`, `exhaustive`, or `incomplete`. `identified` runs checks for known affected services. `exhaustive` is allowed only when dependency uncertainty remains and both enumeration and check discovery are complete; it selects the whole potential-service universe. `incomplete` records specific gaps and blocks admission. See [service-coverage.md](service-coverage.md) and its schema for the evidence fields and supported adapter boundaries.

Run a stage as one unfiltered invocation: `gates run --stage base` or `gates run --stage candidate`. The invocation materializes one disposable checkout and may reuse a successful local execution only when stage, manifest, pinned source identity, exact command and working directory, scope, declared source capabilities, declared environment, and timeout all match. Each manifest obligation still receives its own reservation, log, evidence entry, and gate association. Remote obligations always validate and execute independently.

Between gates, AL checks tracked content, the logical index, Git metadata, and ignored output. A successful check that creates only ignored scratch output keeps its evidence, discards the checkout and reuse cache, and causes the next executable gate to use a fresh checkout from the same pinned candidate. During this post-execution check, ignored generated symlinks are inspected without following them; if any appear, the successful gate keeps its evidence and the checkout is immediately discarded, with no reuse or subsequent launch in that checkout. Unsafe links present at initial capture, candidate materialization, or launch boundaries, and execution-relevant metadata changes, still fail closed. AL never cleans or modifies the source repository to recover a scratch checkout.

Candidate capture continues to include every candidate path, including vendored content. A gate scope may be narrow when its sourced dependencies justify that scope; it does not narrow complete candidate integrity or remove vendor paths from capture.

Gate discovery records obligations from source files and rules before implementation. CI jobs are identified by the pair `source.path` and `source.job`, and are bound to the source file hash. A job obligation carries its affected units, selected input paths, and the workflow/include dependency files needed to evaluate it. The manifest must preserve selected, anticipated, and previously declared paths and units. A replacement cannot erase a known job or narrow its required scope. Map each sourced job to its actual local or remote verification; do not infer a successful remote job from local evidence. Scanned implementation files are discovery inputs used to derive consumers and affected units; they are not policy rules. Body-only edits can invalidate evidence for affected consumers without changing the sourced rule set. Recompute those consumers and scopes at admission.

Remote lookup output is validated before provenance is read: the response and its `pipeline` and `commit` values must be objects; job and pipeline IDs must be positive integers (booleans do not count); job name, commit ID, and status must be nonempty strings; and an optional `web_url` must be a string or null. A non-null pipeline project ID must be a positive integer or nonempty string and match the manifest's project; omission or null remains supported for providers that do not return it. Malformed JSON, unsupported field types, or mismatched identity produce `INFRA`, preserve the lookup output in the log, and finalize the reservation rather than leaving evidence `RUNNING`. Only a matching job, project when supplied, pinned commit, and successful status can pass.

Local and remote gate processes are owned before spawn and run in process groups. On interruption or termination, AL stops and reaps owned descendants, drains their output, and finalizes the reservation as `INFRA` with its log and gate association before propagating cancellation. Finalization is serialized under the state lock; a cancelled operation cannot remain `RUNNING` or be recorded as a late `PASS`.

Local base and candidate gates run in a disposable checkout. Before overlaying candidate content, after the overlay, and before launch, the checkout is checked for unsafe symlinks. Relative links and chains are allowed only when they resolve to existing files or directories inside the checkout; `..` is allowed only while containment is maintained. Absolute, escaping, dangling, cyclic or excessive chains, unsupported targets, and `.git` paths are refused at these boundaries. After a successful gate, ignored generated symlinks are classified with non-following metadata inspection and force immediate checkout discard; nonignored drift and execution-relevant metadata changes remain failures. Gate working directories must also resolve to an existing contained directory outside `.git`. A rejected materialization is `INFRA` with no gate launch and no materialized fingerprint; it is not a gate failure or generated drift.

The bounded YAML reader handles the documented literal subset only. Dynamic includes, unsupported YAML constructs, unresolved anchors, and expressions outside the supported grammar remain `UNRESOLVED`; they are not treated as absent jobs or as satisfied obligations. Local includes are followed with cycle, path, and count bounds. Job names and `source.job` are the concrete names from the merged sourced job graph. Include and workflow conditions are evaluated with three-valued results, so unknown conditions retain the obligation. Workflow `auto_cancel` is recognized only as scheduling metadata; cancellation settings do not remove job obligations.

Resolve includes, inheritance, and references while retaining every consulted source. Before considering an exclusion, preserve cumulative uncertainty from conditional definitions and unresolved workflow rules; malformed stage/environment structure, legacy `only`/`except`, and unsupported or malformed rule syntax also remain unresolved. A later unconditional definition cannot erase uncertainty from an earlier conditional contribution.

For a structurally valid job with trustworthy definition provenance, validate the complete supported `rules` list before applying its ordered first-match result. A conclusively false result, including a final `when: never`, omits the job from verification obligations. An unknown result remains `UNRESOLVED`; a true result, or a job without rules, proceeds to release/verification classification. This ordering lets known-false jobs with a valid custom stage or `environment.action: prepare` be excluded without guessing what their selected execution would do. If selected, those unsupported release identities remain `UNRESOLVED`; no prepare action becomes executable verification. Definite release stages and literal deployment environments with `action: start` or `action: stop` remain excluded, while verification jobs remain obligations. A release-like name without decisive stage or environment semantics stays `UNRESOLVED`.

Conditional-definition provenance is cumulative across includes, repeated definitions, inheritance, and `!reference` dependencies. If uncertainty could change whether a job exists or applies, retain the concrete job as `UNRESOLVED` over all selected task inputs and retain every contributing source/controller as a dependency. Proven-false includes contribute no definition; proven-true includes retain deterministic merge behavior. Source dependencies remain inventoried even when supported rules exclude a job, so changes to consulted rules invalidate prior manifests normally. Admission and currency use this same sourced inventory, so a replacement manifest cannot mark an uncertain obligation APPLICABLE or NOT_APPLICABLE.

Selected paths under `services/<service>/alembic/versions/` are migration changes, including deleted revisions and committed changes present in the candidate path inventory. They require the complete rollout assessment: expand/contract, deployment order, aggregator environment propagation, consumer deployment, and DLQ/redrive. Path matching is based on normalized components, so unrelated paths that merely contain a `versions` substring do not trigger this requirement.

A manifest may declare `ci_context` as `{ "profile": "merge_request_quality", "source": <typed artifact reference> }`. The referenced `ci-context` data artifact contains only `schema_version`, `profile`, the current `session_id`, `run_id`, `task_hash`, and `selection` provenance (`label` and optional `source_sha256`). It is content-addressed and bound to the active run and task. The task hash is derived from the immutable original plus verified amendment prefixes. An intact context tied to an earlier prefix may be recognized as historical while checking currency so the affected manifest can be replanned; it cannot supply the profile to a newly accepted manifest. Corrupt artifacts, unsupported/invented revision hashes, foreign runs, and mismatched bindings refuse. The artifact carries no variable map, secret, pipeline result, or execution evidence. The supervisor selects the profile and records provenance by capturing the JSON bytes with the existing `al_artifacts.snapshot_bytes(session_id, raw, "ci-context", source)` API, then includes that returned typed reference in the manifest. The Architect is read-only and does not choose or edit the context. See `schemas/ci-context-artifact.json` and `examples/ci-context-artifact.json`; the example is a template whose identity/hash placeholders must be replaced with current values.

`merge_request_quality` is a fixed planning profile, not a claim that CI ran: `CI_PIPELINE_SOURCE` is `merge_request_event`; `CI_MERGE_REQUEST_ID` is present for truthiness checks but its value is unknown; `CI_COMMIT_BRANCH`, `FASTLANE`, `BRANCH_ENV_CLEANUP`, and `SONAR_SCAN` are absent. Every other variable remains unknown. It does not import ambient process environment. Unknown variables, an unsupported profile name, malformed expressions, or unsupported syntax stay unresolved. The expression reader accepts a bounded boolean subset (variable truthiness, `==`/`!=` against quoted literals, `&&`, `||`, and parentheses) with three-valued evaluation. Presence without a concrete value cannot satisfy arbitrary equality. Regexes, variable expansion, and arbitrary shell evaluation are outside the contract. YAML input, include count/depth, expression size/token/depth, and path matching are bounded; input over those limits and unsupported syntax stay unresolved rather than being approximated. Glob/path matching is bounded and rooted in the repository; dynamic paths and unsafe or unsupported patterns remain unresolved.

The existing CLI flow is unchanged: `gates discover --paths-file <json> --base <pinned-base>` records the sourced inventory and `gates plan --file <manifest>` records an explicit plan. There is no new CLI or ambient environment switch; the supervisor prepares the artifact with the existing snapshot API and places its typed reference in the manifest before planning. The profile is applied consistently to workflow, local-include, and job rules while retaining ordered first-match behavior, changes, inheritance, and references. A source-proven excluded workflow does not become an empty satisfied inventory. Context and profile are part of manifest identity: changing either requires a replacement manifest and fresh base/candidate evidence under the existing recovery rules. Supplying the optional typed context changes only planning applicability. It does not create CI jobs, execute recipes, access GitLab, or replace `gates run`, remote evidence, base-gate decisions, or candidate-gate requirements. A remote job still requires actual project, job, pipeline, commit, and successful-status provenance; a planning profile never manufactures it. If context or applicability is unknown, resolve the source semantics or keep the obligation unresolved before advancing.

Every `writer start` rechecks current manifest currency and applicable base readiness under the admission lock, then validates its declared paths against both the manifest and a fresh prospective inventory. An exact file entry covers only that file. A declared directory covers its descendants by path components, and `.` covers the repository; a file does not grant sibling, parent, or similarly prefixed directory coverage. Prospective units, sourced rules, consumer obligations, and CI jobs must be covered before the writer is recorded. A new path, unit, rule, or unresolved obligation is refused without changing state until a valid replacement plan and its base gates are ready. Ordinary edits within an already covered file or directory do not require replanning by themselves.

When source rules or the derived obligation inventory become stale during an unfinished exceptional phase (`PSEUDOCODE`, `PLAN_CONFLICT`, `IMPLEMENTATION`, `REWORK`, or `CORRECTION`), ordinary replanning is allowed only after `SPEC_READY` and while no writer or check is active or unresolved. AL records a checkpoint-bound recovery marker and accepts a replacement manifest without changing the retained phase or its completion history. A current manifest does not grant this path. Planning does not clear recovery: current obligations and applicable base gates must pass before phase advancement or a new writer. Present but corrupt recovery markers remain hard refusals.

Prospective coverage is evaluated for the replacement request before deciding whether an extension is needed. Replacement is justified by stale sourced rules or a demonstrated gap in prospective paths/obligations, not by an unchanged manifest. Planning preserves the retained phase and completion history; it does not grant a writer until current currency, coverage, and applicable base readiness all pass.

## Gitlink evidence capabilities

Gate manifests may declare an optional `sources` array on each gate. Evidence planning and execution accept the same declarations through `--sources-file <json>`, where the file contains an array of `{ "path": "vendor/lib", "capability": "parent-entry" }` objects. Each path is normalized relative to the parent repository and identifies a gitlink boundary. Omission is equivalent to an empty array for ordinary scopes.

`parent-entry` declares that a check depends on the parent repository's gitlink entry. AL fingerprints the staged and effective parent pointers, so a pointer change invalidates evidence. It proves the selected pointer only; the child repository's files and uncommitted content remain opaque. Broad scopes such as `.` do not implicitly claim child-content coverage. Any scope intersecting a gitlink must declare its capability, including when the scope is the gitlink path itself. Scope or working directory inside a child repository requires child-content verification.

`child-content` is reserved for an execution rooted in the child repository. This version reports that capability as unsupported and directs the operator to run AL from that child root; it does not import child-run evidence into a parent run. AL does not infer dependencies by inspecting command strings. Existing evidence with no `sources` remains usable for ordinary scopes, while legacy evidence whose scope overlaps a gitlink cannot establish which content it covered and is treated as unresolved until rerun with an explicit capability.

Parent snapshots and isolated candidates materialize the effective parent gitlink pointer without initializing, fetching, or copying child contents. The parent index pointer and an initialized child's current `HEAD` are recorded separately; the effective candidate uses the latter. Dirty, unavailable, or failed child inspection is reported as uncaptured child state. Checks disjoint from that boundary may still run, but approval cannot claim that opaque child changes were reviewed or tested. Because a complete-candidate snapshot cannot safely distinguish pre-existing child dirt from task changes, AL reports the limitation and blocks approval when such child work is present. Isolation reproduces parent entries and ordinary files only; it does not reconstruct child worktrees or their indexes.

## Review-hook state

A repository review hook that writes under `.git` (for example `.git/codex-review`) is supported only through an explicit gate declaration: `"review_state": {"path": ".git/codex-review"}` on an applicable local gate. The path is one isolated `.git/<name>` location (up to three literal segments); Git's own metadata (`objects`, `refs`, `hooks`, `index`, `config`, `HEAD`, `logs`, `worktrees`, ...) is never accepted, and `.git` writes in general remain refused.

In the disposable checkout the declared location must be absent before each execution, so stale or foreign review state cannot carry into a gate. After the command ends (and its process group is reaped) whatever the hook left there is captured, including its absence, directory modes and file bytes and modes, bounded to 4,096 entries / 16 MiB; symbolic links, hard-linked files, special files and files that change during capture are refused. The location is then removed, after which the ordinary metadata drift check still fails any other `.git` write. The capture is retained as an immutable `review-hook-state-v1` artifact bound to the run, evidence reservation, manifest, gate, stage, invocation, execution identity and candidate (or base) fingerprint, and the evidence records its digest metadata. Gate validation requires that artifact to be intact and bound to the current candidate; missing, stale, foreign or altered state invalidates the gate. Declared-state gates always execute fresh rather than reusing an execution receipt, and the declaration is part of the execution key and preserved across rediscovery. The source repository's own `.git` never receives review state.

## Baseline exceptions

`fix` commits the task to repairing a failed base gate and `stop`/`defer` stop the run. A distinct `gates decision --id <gate> --action exception --source <explicit authorization> --reason <why>` records that the current exact unchanged-base failure of one gate is accepted for implementation admission while its repair stays outside the task. It requires the latest current-manifest base evidence of that gate to be FAIL with an intact log, and writes an append-only, immutable `baseline-exception-v1` authorization artifact binding the session, run, pinned base, manifest, gate command (`argv`, `cwd`, `scope`, `sources`, execution kind), declared environment names and fingerprint, failed evidence, reservation, exit, log hash and execution identity.

Base readiness accepts that one failure only while every bound value still matches; a new manifest or base run, a changed command or declared environment value, an altered log or a forged artifact makes the exception stale and the gate blocks again. The evidence stays FAIL and `gates status` lists exceptions separately from gate results. An exception satisfies no other obligation: `gates run --stage base --resume` still executes every remaining base gate, and other failures still block. Candidate gates always run and report failures honestly, so an exception never approves a candidate with red checks.
