---
description: "Start the AL Engineering Harness for a request (only entry point)"
argument-hint: <request>
---

Run `uv run harness start "$ARGUMENTS"` from the repository root and relay its output verbatim, including the task id and the proposed complexity. Tell the developer that the proposal is only a recommendation and can be overridden with the `override:` command printed in the output. Then run `uv run harness investigate <task id>` with the task id from that output and relay the report verbatim (it is read-only: verified facts, assumptions and unresolved questions stay separate).

Then open the web dashboard for that task. From the repository root, start `uv run python -m harness.dashboard <task id>` as a background process: it keeps serving until it is stopped, so do not wait for it to exit. Relay the line it prints, `dashboard: http://127.0.0.1:<port>/ · task <id> · Ctrl-C stops it`, so the developer has the URL; it also opens the page in the browser. The dashboard listens on 127.0.0.1 only, on a free port chosen each run, and it writes only the diagram versions recorded by the Diagram Service when the design changes and the comments the developer adds, resolves or re-opens there (otherwise it reads the same task state and specs as the CLI). Start it once per task, and stop it (Ctrl-C or SIGTERM, which prints `dashboard stopped`) when the task is done or the developer switches to another task. If it prints `could not open a browser; open <url> yourself`, give the developer that URL. If it exits with `harness dashboard: <error>`, relay the error and carry on with the CLI, which does not depend on the dashboard.

Then run the requirements interview. You only relay and record; the CLI owns the question state and the checklist, and you never answer a question for the developer.

1. Ask the developer to confirm or override the proposed complexity (`uv run harness classify <id> <level>`), then run `uv run harness phase <id> next` to enter the interview phase.
2. Loop: run `uv run harness interview next <id>` (add `--group` when the developer prefers one topic at a time) and relay each question verbatim.
   - Plain question: ask it, then record exactly what the developer typed with `uv run harness interview answer <id> <qid> <text>`.
   - `(decision)` question with `recommendation needed`: write a recommendation and its rationale from the investigation facts, register it with `uv run harness interview propose <id> <qid> --title "<title>" --recommendation "<text>" --rationale "<why>" --impact "<consequences of choosing it>"` (title, recommendation and rationale are required; `--impact` carries the consequences and is stored with the decision record), present it, and record the developer's verdict with `uv run harness interview decide <id> <pid> accept|reject|modify` (`modify` needs `--response "<developer's change>"`). A recommendation is never a requirement until the developer accepts or modifies it. Accepting or modifying a `(decision)` recommendation records it automatically in `docs/decisions` (the output ends with `recorded DEC-NNNN v1 -> <path>`; relay it). Rejecting records nothing.
   - "I don't know", unsure or deferred: run `uv run harness interview unknown <id> <qid>`. Never fill the gap with an assumption. The question stays open and blocking, and `next` moves on to the next one.
   - Only when the investigation report or an approved decision already answers a question, run `uv run harness interview skip <id> <qid> --source decision --ref DEC-xxxx` or `--source codebase --ref "<file or fact>"`, and tell the developer what was skipped and why. Use `--source not_relevant --ref "<reason>"` only when the developer says it does not apply.
   - A follow-up you need: `uv run harness interview ask <id> <topic> <text> [--decision]`.
3. After each round run `uv run harness interview checklist <id>` and relay it verbatim. Entries with a `catalogue:<key>` ref are due questions not asked yet.
4. When `next` prints `no questions left to ask; N open question(s) stay unresolved`, the remaining questions were deferred: show the checklist and ask the developer whether to revisit them. `no open questions` means nothing is open. Stop when the developer says so or nothing blocks; show `uv run harness interview summary <id>` at the end.

Then run the architecture design. You only relay and record; the CLI owns the design state and the coverage check, and you never add design content the developer did not state or approve.

5. Run `uv run harness phase <id> next` to enter the design phase. The eight sections are `components`, `responsibilities`, `interactions`, `data_flow`, `interfaces`, `configuration`, `failure_handling` and `required_behaviour`.
6. Draft recommendations from the investigation report and `uv run harness interview summary <id>`. Register each one with `uv run harness design propose <id> <section> "<text>" --rationale "<why>"` (add `--delegated` for details AL may decide, such as class and method names or file placement), present it, and record the developer's verdict with `uv run harness design decide <id> <eid> accept|reject|modify` (`modify` needs `--response "<developer's change>"`). A recommendation is never part of the design until the developer accepts or modifies it. The dashboard draws diagrams only from notation lines in effective design entries, so a recommendation may include such a line only for what the developer stated or approved, never to add structure of your own. The six forms, one per line, are `component <name>[: <description>]`, `connect <from> -> <to>[: <label>]`, `message <from> -> <to>: <text>`, `flow <from> -> <to>[: <data>]`, `state <machine>: <from> -> <to>[: <event>]` and `deploy <component> @ <node>`; every other line is prose and draws nothing.
7. Record what the developer states verbatim with `uv run harness design add <id> <section> "<text>"` (`--delegated` when the developer leaves the detail to AL). When the developer says a section does not apply, run `uv run harness design none <id> <section> --reason "<developer's reason>"`. Correct a mistake with `uv run harness design withdraw <id> <eid>`.
8. After each round run `uv run harness design coverage <id>` and relay it verbatim; keep going until it says `blocking: no` or the developer stops. At the end show `uv run harness design show <id>`.

Redesign loop: when the developer has commented on the diagrams in the dashboard, run `uv run python -m harness.redesign <id>` and relay its output verbatim. It is read-only and lists the open comments (`#<comment id> · <kind> · <element> · version <n>`, then the comment text indented); `no open comments` means there is nothing to do. Draft a fix for each open comment only from the comment's text and what the developer has stated; a clarification may need an answer and no design change at all. If the task is already past the design phase, route back with `uv run harness phase <id> back design --reason "<comment #n>"` only on the developer's say-so. Register the corrected entry with `uv run harness design propose <id> <section> "<text>" --rationale "<why>"` (a recommendation that carries the corrected notation line) and record the developer's verdict with `uv run harness design decide <id> <eid> accept|reject|modify`; the developer decides, never you. Only after `accept` or `modify` withdraw the entry it replaces with `uv run harness design withdraw <id> <eid>`. Then run `uv run python -m harness.redesign address <id> <comment id>...` for exactly the comments the accepted change handles, and relay its output verbatim. It first records the changed design as a new diagram version, then marks every named comment addressed in one transaction (all or nothing), so an id that is unknown or already resolved refuses the whole batch; a rerun is safe. Tell the developer to review the revised diagrams next to the previous version in the dashboard (the Compare versions section highlights what was added, removed or changed) and to resolve or re-open each comment there. A re-opened comment is open again and comes back in the next list. Never address a comment the change did not handle, never resolve or re-open a comment for the developer, and then continue with the usual `phase next` steps.

9. Changing an earlier decision never edits its file. Run `uv run harness decision change <id> <DEC-id> --decision "<new decision>" --rationale "<why>" --impact "<consequences>"`, relay the preview verbatim (original rationale and impact, what references it, the consequences of the change), and only then record the developer's verdict with `uv run harness decision decide <id> <cid> accept|reject|modify` (`modify` needs `--response "<developer's change>"`). Never decide a change for the developer. A decision the developer states directly, outside a recommendation, is recorded with `uv run harness decision record <id> --title "<title>" --decision "<text>" --rationale "<why>" [--impact "<consequences>"]`.
10. Cross-project hints come only from `uv run harness decision suggest <id> --from <repo>` with a repository the developer named. It is read-only; relay the result as suggestions only, and adopt one only by proposing it in the interview for the developer to decide.

11. Then plan the tests. You only relay and record; the CLI owns the test-plan state and you never add a scenario the developer did not state or approve. Run `uv run harness phase <id> next` to enter the `test_plan` phase. Draft scenarios only from `uv run harness interview summary <id>`, `uv run harness design show <id>` and the investigation report, and only the ones relevant to the task, in the categories `unit`, `integration`, `e2e`, `regression`, `edge_case` and `failure`. Register each with `uv run harness testplan propose <id> <category> "<text>" --rationale "<why>" --covers Q<n> [--covers E<n> ...]` (every recommendation must cite an answered requirement `Q<n>` or an effective design entry `E<n>`; references are case-sensitive), present it, and relay the developer's verdict with `uv run harness testplan decide <id> <sid> accept|reject|modify` (`modify` needs `--response "<developer's change>"`). Record what the developer states with `uv run harness testplan add <id> <category> "<text>"`, change one with `uv run harness testplan edit <id> <sid> ...` and remove one with `uv run harness testplan withdraw <id> <sid>`. Use a mock only with `--mock "<target>" --mock-reason "<why>"` (both are required). Whenever a mock would stand in for behaviour the task must implement, run `uv run harness testplan flag <id> <sid> --reason "<what it hides>"` and tell the developer; clear it only with `testplan flag <id> <sid> --clear --reason "<why>"` on the developer's say-so. After each round run `uv run harness testplan review <id>` and relay it verbatim. Run `uv run harness testplan approve <id>` only on the developer's explicit approval; it is refused while anything is pending or flagged or the plan is empty (relay that and do not work around it). Any later change, or a flag raised after approval, needs a new `testplan approve`. At the end show `uv run harness testplan show <id>`.

12. Then run the final design review. You only relay; the CLI owns the check (SPEC §3 step 6) and you never work around it. Run `uv run harness review <id>` and relay it verbatim, including every `BLOCKED` item and its `→` hint. It is read-only and exits 1 while anything blocks. When it blocks, show the printed hint and route back (`uv run harness phase <id> back <phase> --reason "<why>"`) only on the developer's say-so; never route back, answer, decide or fill a gap on your own initiative. `n/a` items (diagram comments are Phase 2) are not a gap. When nothing blocks, run `uv run harness phase <id> next` to enter `final_review` and again to enter `approval`. The second is refused with the same report while anything blocks (relay it; do not work around it), and when it passes it prints `final design review passed (checkpoint recorded)`.

13. The specification is `uv run harness spec ...`. You only relay; the CLI renders it from what the developer stated or approved, and you never edit a file under `docs/specs/` yourself. Preview it with `uv run harness spec show <id>` and relay it verbatim. Write a draft with `uv run harness spec draft <id>` only when the developer asks for one. Run `uv run harness spec approve <id>` only on the developer's explicit approval, and only once the task is in the `approval` phase (outside it the command exits 1 with a hint; relay that and do not work around it). Relay its output verbatim, including the revision and the working tree count; if the working tree is not clean, tell the developer so. Never approve on your own initiative. Check sealed files with `uv run harness spec verify <id>` and relay the result verbatim, including any `MODIFIED` line.

14. Approve & Implement is `uv run harness approve <id>`. You only relay. Run it only on the developer's explicit "Approve & Implement" and only once the task is in the `approval` phase (outside it, or while the final design review blocks, it exits 1 and writes nothing; relay that and do not work around it). It seals a new `v<N>.md` and records the approval that authorizes the handoff; relay its output verbatim, including the `approval #<n> recorded` line and any `superseded` line. Never run it on your own initiative, and never treat `spec approve` as an approval. The task then waits for Phase 3: do not start implementing, and do not launch AL. `uv run harness show <id>` prints an `approval:` line (`none`, `current` or `stale` with the reason); relay it verbatim, and if it is stale, tell the developer and run `approve` again only on their say-so.

15. To continue an interrupted task, run `uv run harness resume <id>` (or `uv run harness resume` to list the resumable tasks) and relay its output verbatim. It is read-only and derives the resume point from the committed state, so it never changes anything. Continue at the printed `next:` command, and when a pending question is printed, re-ask it verbatim and record only what the developer types: never answer it yourself. If a `note:` reports an unrecorded draft, tell the developer; rewrite it with `uv run harness spec draft <id>` only on their say-so. `nothing to resume` means the task is approved and waits for Phase 3: do not start implementing, and do not launch AL. Once the developer picks the task to continue, open the dashboard for it the same way.

Do nothing beyond this; the harness is activated only by this command and never implicitly (SPEC §2, AC 1).
