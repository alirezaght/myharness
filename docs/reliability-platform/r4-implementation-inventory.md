## Setup and dispatch ownership used by typed consumers

`auto_prepare()` is the metadata-only bridge from an AL registration to dependency setup. It derives bounded repository-relative setup requests from the task's files, validates task/revision metadata with output verification disabled, and records concrete pending requests with a `Queued` outcome. It does not read target dependency manifests or launch an installer under the outer AL command's Attempt. `Queued` means setup is pending, not that dependencies were checked, prepared, or tested.

`OperationController.tick()` handles setup only when no Attempt is ambient. It resumes an explicitly retained owning setup Attempt after revalidating its authority, or routes a fresh request through the public `dispatch(..., "environment_operation", request)` path even when no optional policy binding exists. It does not nest admission inside an unrelated AL Attempt or transfer that Attempt to the setup request. The actual `prepare()` handler checks that the current Attempt is an `environment_operation` for the same execution, principal, task and revision before reading target manifests. Legacy liability and unsupported native/process closure remain unresolved through polling or cancellation.

The implementation/test seams are `harness/task_environment.py::auto_prepare`, `prepare` and `task_unit`, plus `harness/execution_operations.py::dispatch`, `al_command` and `tick`. Focused setup coverage is `tests/test_agent_contracts_setup.py`, alongside the retained assertions in `tests/test_task_tooling.py`, `tests/test_execution_operations.py` and `tests/test_execution_continuity.py`. E51 is the genuine pre-fix causal red; E56 and E61 are preserved fixture/postcondition failures; E59/E60 are functional passes but stale after a later test-only correction. See the current post-correction entries in [implementation-progress.md](implementation-progress.md).

## Correctness boundary

Assignment presentation/output publication validate the exact immutable buffer and preserve legacy uncertainty. They may report `immutable_snapshot_validated` and `mutable_source_not_checked`. Actual current source consumption is a separate protocol: metadata-only preflight, strict source claims reserved on the existing attempt before file/hash reads, predecessor and pending-native launch checks, same-connection current-epoch revalidation, claims retained through use, and conservative no-start/closure evidence. Only this path may report `coordinated_source_consumption`; `legacy_uncoordinated` is not a success.

No R4 artifact status grants authority or completion. Authored work can remain unverified and consumable where existing policy permits. General writer start, task-authored/task-agent lifecycle commands, outer native processes, unsupported old bridges, other databases and uninstrumented external actors remain outside the claimed qualification. See [R4 API limits](r4-api-contract.md#immutable-exchange-and-mutable-source-are-different-guarantees).
